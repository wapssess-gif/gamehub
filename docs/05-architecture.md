# Архитектура и технологический стек

Контекст: pet/учебный проект, только веб (адаптивная вёрстка), данные
об играх — из внешнего API. Ниже — варианты стека с плюсами/минусами
и рекомендация. Финальный выбор — за пользователем, документ не
предполагает, что решение уже принято.

## Общая архитектура (не зависит от стека)

```
Браузер (SPA/SSR)
     │
     ▼
Веб-сервер / API-слой  ──▶  Внешнее игровое API (IGDB или RAWG)
     │                          (кэшируется в таблице Game)
     ▼
База данных (PostgreSQL)
     │
     ▼
Файловое хранилище (скриншоты, аватары)
```

- Внешнее API вызывается на бэкенде (не с клиента) — чтобы не палить
  API-ключ и иметь контроль над rate-limit и кэшированием.
- Файлы (скриншоты, аватары) не хранятся в самой БД — только ссылки.

## Вариант A — Next.js full-stack (рекомендуется для этого проекта)

- **Frontend**: Next.js (React) + TypeScript, Tailwind CSS.
- **Backend**: API-роуты того же Next.js-приложения (или отдельный
  слой на tRPC) — не нужен отдельный сервер на старте.
- **БД**: PostgreSQL + Prisma ORM.
- **Auth**: NextAuth.js (email/password + Google/Steam OAuth "из коробки").
- **Хранилище файлов**: Vercel Blob (аватары); Supabase Storage / Cloudflare R2 — вариант для скриншотов.
- **Хостинг**: Vercel (frontend+API) + Supabase/Neon (Postgres) — есть
  бесплатные тарифы, подходит для pet-проекта.

Плюсы: один язык (TypeScript) на весь стек, минимум инфраструктуры для
старта, много готовых туториалов именно под связку Next.js+Prisma+
NextAuth — хорошо для обучения.
Минусы: API-роуты Next.js менее гибкие, чем отдельный backend, если
проект вырастет в нечто большее, часть логики придётся выносить.

## Вариант B — Разделённые frontend и backend (SPA + REST/GraphQL API)

- **Frontend**: React (Vite) + TypeScript + Tailwind.
- **Backend**: Node.js + Express или Fastify (или NestJS для более
  строгой архитектуры), REST или GraphQL API.
- **БД**: PostgreSQL + Prisma или TypeORM.
- **Auth**: собственная JWT/сессионная реализация или Passport.js.
- **Хостинг**: frontend — Vercel/Netlify, backend — Render/Railway/Fly.io.

Плюсы: чёткое разделение слоёв, ближе к тому, как устроены "взрослые"
production-системы — хорошо, если цель обучения именно это.
Минусы: больше инфраструктурной работы на старте (CORS, деплой двух
частей, отдельная auth-логика).

## Вариант C — Python/Django full-stack

- **Backend+шаблоны или DRF**: Django + Django REST Framework.
- **Frontend**: Django Templates (проще) или React поверх DRF API
  (гибче, но больше работы).
- **БД**: PostgreSQL (Django ORM).
- **Auth**: встроенная система пользователей Django + django-allauth
  для OAuth.
- **Хостинг**: Railway/Render/PythonAnywhere.

Плюсы: Django даёт очень много "из коробки" (админка, auth, ORM,
миграции) — быстрый старт, если ближе Python, чем JS.
Минусы: если позже понадобится богатый интерактивный UI (лента
активности, живые счётчики), придётся либо писать много JS поверх
шаблонов, либо переходить на API+React (то есть фактически к варианту B).

## Сравнение

| Критерий | A: Next.js full-stack | B: React SPA + отдельный API | C: Django |
|---|---|---|---|
| Скорость старта | Высокая | Средняя | Высокая |
| Обучающая ценность (совр. веб-практики) | Высокая | Высокая | Средняя |
| Простота деплоя для pet-проекта | Высокая | Средняя | Средняя |
| Гибкость при росте проекта | Средняя | Высокая | Средняя |
| Порог входа, если стек новый | Средний | Средний/высокий | Низкий (если знаком Python) |

## Рекомендация

Для целей проекта (pet/учебный, только веб, MVP с трекингом библиотеки
и статистикой) — **Вариант A (Next.js + PostgreSQL + Prisma +
NextAuth)**. Он даёт быстрый путь от документации к рабочему MVP,
не требует поднимать отдельный backend-сервис, и всё ещё учит
современным практикам full-stack разработки. Переход к варианту B
(вынос API отдельно) в будущем не потребует переписывать модель
данных — только слой API.

### Решение (2026-09-04)

Выбран **Вариант A**. Финальный стек для MVP:

- **Frontend/Backend**: Next.js (App Router) + TypeScript + Tailwind CSS.
- **БД**: PostgreSQL + Prisma ORM.
- **Auth**: NextAuth.js (email/password на старте, OAuth Google/Steam — этап 2).
- **Внешнее игровое API**: RAWG (см. ниже).
- **Хранилище файлов**: Vercel Blob — для аватаров профиля (F3). Скриншоты
  (этап 3) при необходимости можно вынести в Supabase Storage / R2, но
  Vercel Blob подойдёт и для них. Токен `BLOB_READ_WRITE_TOKEN`; без него
  загрузка аватара просто отключается, остальное работает.
- **Хостинг**: Vercel (app) + Neon/Supabase (Postgres).

## Внешнее игровое API — выбор между IGDB и RAWG

| | IGDB | RAWG |
|---|---|---|
| Авторизация | Через Twitch Developer (OAuth client credentials) | Простой API-ключ |
| Полнота данных | Очень подробная (метакритик, франшизы, DLC) | Хорошая, включая скриншоты и рейтинги магазинов |
| Лимиты бесплатного тарифа | Достаточные для pet-проекта | Достаточные для pet-проекта |
| Сложность интеграции | Выше (нужен Twitch app + токен) | Ниже (сразу API-ключ) |

Для pet-проекта и быстрого старта — **RAWG проще для первой интеграции**;
если в приоритете более богатые данные (франшизы, DLC, метакритик) —
**IGDB**. Оба варианта укладываются в модель `Game` из
[04-data-model.md](04-data-model.md) (поле `external_source` как раз
для этого).

**Решение (2026-09-04): RAWG.** Приоритет — быстрый старт MVP; переход
на IGDB (или добавление его как второго источника) остаётся возможным
позже благодаря полю `external_source`.

## Нефункциональные аспекты архитектуры

- Все секреты (API-ключи, DB URL, JWT secret) — через переменные
  окружения (`.env`, не в репозитории).
- Кэш ответов внешнего API — на уровне таблицы `Game` (`cached_at`),
  без отдельного Redis на этапе MVP (это добавление сложности, не
  оправданное для pet-проекта на старте).
- Миграции БД — через инструмент ORM (Prisma Migrate / Django
  migrations), а не ручные SQL-скрипты.
